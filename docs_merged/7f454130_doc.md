### 1. Module Purpose and Architectural Position

The module `vigia/cli.py` constitutes the primary command-line interface (CLI) control layer within the VIGÍA digital forensics framework. Its architectural mandate is to serve as the exclusive deterministic gateway through which human investigators translate structured, high-level investigative directives into unambiguous, low-level system instructions. Operating within a fixed footprint of 5956 bytes, this module functions as a lexical–syntactic–semantic transducer that eliminates interpretive ambiguity during the ingestion of forensic commands. Unlike general-purpose CLI parsers that may tolerate nondeterministic behavior through fuzzy matching or heuristic auto-completion, `vigia/cli.py` is engineered under a strict deterministic contract: for any given input string and system state, the module produces exactly one parse tree, one execution path, and one auditable log entry. This property is foundational to the admissibility of digital evidence under the *Daubert* standard and the repeatability requirements stipulated in ISO/IEC 27037:2012.

Architecturally, `vigia/cli.py` occupies Layer 3 (Presentation and Control) of the VIGÍA reference model, mediating between the human investigator at Layer 4 and the forensic kernel services at Layer 2. It does not perform evidence acquisition, cryptographic hashing, or chain-of-custody storage directly; rather, it orchestrates calls to `vigia/acquisition.py`, `vigia/custody.py`, and `vigia/orchestrator.py` through a strictly validated command dispatch protocol. By centralizing all user-facing control logic within a minimal, auditable surface, the module ensures that every interaction with the forensic substrate is subject to syntactic validation, privilege verification, and tamper-evident logging prior to execution.

### 2. Mathematical Foundations

The design of `vigia/cli.py` rests on formal language theory and deterministic state-transition systems. Let the input alphabet be defined as the UTF-8 character set Σ. The set of all possible command strings is then Σ*. The module implements a deterministic lexer ℒ that maps an input string *c* ∈ Σ* to a finite sequence of tokens τ = (t₁, t₂, …, tₙ) ∈ T*, where T is the token vocabulary defined by the VIGÍA command grammar G_vigia. Formally:

ℒ: Σ* → T*

The parser 𝒫 constitutes a deterministic pushdown automaton (or equivalent LL(k) recursive descent parser) that consumes τ and produces an abstract syntax tree (AST) *a* ∈ 𝓐, where 𝓐 is the set of all well-formed ASTs:

𝒫: T* → 𝓐

Semantic validation is modeled as a predicate function 𝒮: 𝓐 → {0, 1}, where 𝒮(*a*) = 1 if and only if the AST satisfies all contextual constraints (valid evidence identifiers, authorized user credentials, temporally consistent timestamps, and compatible subsystem targets). The set of valid commands is therefore:

𝒱 = { *a* ∈ 𝓐 | 𝒮(*a*) = 1 }

Command dispatch is formalized as a state-transition function Δ. Let 𝓢 denote the global system state space (encompassing environment variables, open evidence handles, and privilege bitmaps), and let 𝓞 denote the space of observable outputs (exit codes, stdout/stderr streams, and log entries). The dispatch function is:

Δ: 𝒱 × 𝓢 → 𝓢 × 𝓞

A core invariant of the module is determinism: for any valid command *a* ∈ 𝒱 and any reachable system state *s* ∈ 𝓢, the transition is a singleton:

|Δ(*a*, *s*)| = 1

This implies that the execution trace is a function, not a relation, ensuring reproducibility.

Chain-of-custody logging is modeled as an injective function Λ that maps each forensic operation to a unique log entry. Let 𝓔 be the evidence identifier space, 𝓤 the user credential hash space, 𝓣 the trusted timestamp space, and 𝓛 the ledger entry space. Then:

Λ: 𝓔 × 𝓤 × 𝓣 × 𝒱 → 𝓛

Each entry λ ∈ 𝓛 is cryptographically bound to its operation through a one-way hash function *H* (typically SHA-256 or SM-3 when operating under GB/T compliance):

λ = *H*(*e* || *u* || *t* || *a* || nonce)

where || denotes concatenation and nonce ∈ ℕ is a monotonically increasing sequence number generated by `vigia/audit.py` to prevent replay attacks.

### 3. Algorithm Description

The operational algorithm of `vigia/cli.py` proceeds through eight strictly ordered phases, each exhibiting worst-case linear or linearithmic time complexity relative to input size *n* = |*c*|.

**Phase 1: Lexical Analysis.** The lexer scans the raw input string *c* character-by-character using a DFA with |Σ| transitions. Tokenization runs in O(*n*) time and O(1) auxiliary space (excluding the output token array).

**Phase 2: Syntactic Parsing.** The recursive descent parser consumes τ according to G_vigia. The grammar is deliberately designed to be LL(1), eliminating backtracking and guaranteeing O(*n*) parse time. The output is an AST *a* whose nodes represent commands, arguments, flags, and target subsystems.

**Phase 3: Semantic Validation.** The validator traverses *a* in post-order, verifying: (i) that all evidence identifiers *e* ∈ 𝓔 exist in the active case registry managed by `vigia/evidence.py`; (ii) that the invoking user *u* ∈ 𝓤 possesses the requisite privilege bitmap *p* for the requested operation class; (iii) that temporal constraints *t*<sub>cur</sub> ≥ *t*<sub>last</sub> hold for append-only custody logs; and (iv) that the target subsystem (e.g., acquisition, custody, orchestration) is in a state accepting new commands.

**Phase 4: Privilege and Integrity Verification.** Before dispatch, the module computes a cryptographic checksum of the AST, *H*(*a*), and verifies it against an integrity manifest maintained by `vigia/hashing.py`. Any divergence aborts execution with exit code ε = 255 and triggers an incident record.

**Phase 5: Atomic Logging (Write-Ahead).** Following the WAL protocol, the module invokes `vigia/audit.py` to persist λ = Λ(*e*, *u*, *t*, *a*) to tamper-evident storage before the operation executes. The log is fsync’d to non-volatile media, ensuring that even catastrophic failure cannot erase evidence of the intent to execute.

**Phase 6: Command Dispatch.** The validated AST is serialized into a canonical inter-module message *m* ∈ ℳ and transmitted via local domain socket or in-memory queue to the target subsystem. The mapping from AST node type to subsystem is injective:

dispatch: {acquisition, custody, orchestration, hash_verify} → {`vigia/acquisition.py`, `vigia/custody.py`, `vigia/orchestrator.py`, `vigia/hashing.py`}

**Phase 7: Execution and Capture.** The target subsystem executes the operation and returns a structured response *r* ∈ 𝓡. The CLI captures the return code ε, stdout stream σ, and stderr stream δ, encapsulating them into the observable output *o* ∈ 𝓞.

**Phase 8: Post-Execution Verification.** The module performs a delta-check between the pre-operation state *s* and post-operation state *s*′, verifying that only the declared side effects occurred. It emits a final log entry λ′ confirming completion or rollback.

5. **Isolation from Nondeterministic Subsystems:** The CLI layer does not sample from random distributions, does not rely on thread scheduling for semantic outcomes, and does not cache results across invocations unless explicitly directed by deterministic cache keys.

Definimos el alfabeto de entrada como el conjunto de caracteres UTF-8 Σ. El conjunto de todas las cadenas de comando posibles es, entonces, Σ*. El módulo implementa un analizador léxico determinista ℒ que mapea una cadena de entrada *c* ∈ Σ* a una secuencia finita de tokens τ = (t₁, t₂, …, tₙ) ∈ T*, donde T es el vocabulario de tokens definido por la gramática de comandos G_vigia. Formalmente:

ℒ: Σ* → T*

El analizador sintáctico 𝒫 constituye un autómata de pila determinista (o su equivalente analizador de descenso recursivo LL(k)) que consume τ y produce un árbol de análisis sintáctico (AST) *a* ∈ 𝓐, siendo 𝓐 el conjunto de todos los AST bien formados:

𝒫: T* → 𝓐

La validación semántica se modela como una función predicado 𝒮: 𝓐 → {0, 1}, donde 𝒮(*a*) = 1 si y solo si el AST satisface todas las restricciones contextuales (identificadores de evidencia válidos, credenciales de usuario autorizadas, marcas temporales consistentes y subsistemas destino compatibles). El conjunto de comandos válidos queda definido, por tanto, como:

𝒱 = { *a* ∈ 𝓐 | 𝒮(*a*) = 1 }

El despacho de comandos se formaliza mediante una función de transición de estados Δ. Sea 𝓢 el espacio de estados del sistema global (que abarca variables de entorno, manejadores de evidencia abiertos y mapas de bits de privilegio), y sea 𝓞 el espacio de salidas observables (códigos de salida, flujos stdout/stderr y entradas de registro). La función de despacho es:

Δ: 𝒱 × 𝓢 → 𝓢 × 𝓞

Un invariante central del módulo es el determinismo: para cualquier comando válido *a* ∈ 𝒱 y cualquier estado alcanzable *s* ∈ 𝓢, la transición constituye un singleton:

|Δ(*a*, *s*)| = 1

Esto implica que la traza de ejecución es una función y no una relación, asegurando la reproducibilidad.

El registro de cadena de custodia se modela como una función inyectiva Λ que mapea cada operación forense a una entrada de registro única. Sea 𝓔 el espacio de identificadores de evidencia, 𝓤 el espacio de hashes de credenciales de usuario, 𝓣 el espacio de marcas temporales confiables y 𝓛 el espacio de entradas del libro mayor. Entonces:

Λ: 𝓔 × 𝓤 × 𝓣 × 𝒱 → 𝓛

Cada entrada λ ∈ 𝓛 se vincula criptográficamente a su operación mediante una función hash unidireccional *H* (típicamente SHA-256 o SM-3 cuando se opera bajo cumplimiento GB/T):

λ = *H*(*e* || *u* || *t* || *a* || nonce)

donde || denota concatenación y nonce ∈ ℕ es un número de secuencia monotónicamente creciente generado por `vigia/audit.py` para prevenir ataques de reproducción.

### 3. Descripción del algoritmo

El algoritmo operativo de `vigia/cli.py` avanza a través de ocho fases estrictamente ordenadas, cada una de las cuales exhibe complejidad temporal en el peor caso lineal o linealítmica respecto del tamaño de entrada *n* = |*c*|.

**Fase 1: Análisis léxico.** El analizador léxico examina la cadena de entrada cruda *c* carácter por carácter utilizando un autómata finito determinista con |Σ| transiciones. La tokenización se ejecuta en tiempo O(*n*) y espacio auxiliar O(1) (excluyendo el arreglo de tokens de salida).

**Fase 2: Análisis sintáctico.** El analizador de descenso recursivo consume τ conforme a G_vigia. La gramática se diseña deliberadamente para ser LL(1), eliminando el retroceso y garantizando tiempo de análisis O(*n*). La salida es un AST *a* cuyos nodos representan comandos, argumentos, banderas y subsistemas destino.

**Fase 3: Validación semántica.** El validador recorre *a* en post-orden, verificando: (i) que todos los identificadores de evidencia *e* ∈ 𝓔 existan en el registro de casos activos gestionado por `vigia/evidence.py`; (ii) que el usuario invocador *u* ∈ 𝓤 posea el mapa de bits de privilegio *p* requerido para la clase de operación solicitada; (iii) que las restricciones temporales *t*<sub>cur</sub> ≥ *t*<sub>last</sub> se cumplan para los registros de custodia de solo-adición; y (iv) que el subsistema destino (por ejemplo, adquisición, custodia, orquestación) se encuentre en un estado que acepte nuevos comandos.

**Fase 4: Verificación de privilegios e integridad.** Antes del despacho, el módulo computa una suma de verificación criptográfica del AST, *H*(*a*), y la contrasta contra un manifiesto de integridad mantenido por `vigia/hashing.py`. Cualquier divergencia aborta la ejecución con código de salida ε = 255 y activa un registro de incidente.

**Fase 5: Registro atómico (Write-Ahead).** Siguiendo el protocolo WAL, el módulo invoca a `vigia/audit.py` para persistir λ = Λ(*e*, *u*, *t*, *a*) en almacenamiento a prueba de manipulación antes de que la operación se ejecute. El registro se sincroniza mediante fsync a medios no volátiles, asegurando que incluso un fallo catastrófico no pueda borrar la evidencia de la intención de ejecutar.

**Fase 6: Despacho de comandos.** El AST validado se serializa en un mensaje canónico intermódulos *m* ∈ ℳ y se transmite mediante socket de dominio local o cola en memoria al subsistema destino. El mapeo desde el tipo de nodo AST al subsistema resulta inyectivo:

despacho: {adquisición, custodia, orquestación, verificación_hash} → {`vigia/acquisition.py`, `vigia/custody.py`, `vigia/orchestrator.py`, `vigia/hashing.py`}

**Fase 7: Ejecución y captura.** El subsistema destino ejecuta la operación y devuelve una respuesta estructurada *r* ∈ 𝓡. La CLI captura el código de retorno ε, el flujo de salida σ y el flujo de error δ, encapsulándolos en la salida observable *o* ∈ 𝓞.

**Fase 8: Verificación post-ejecución.** El módulo realiza una verificación delta entre el estado pre-operación *s* y el estado post-operación *s*′, constatando que solo ocurrieron los efectos secundarios declarados. Emite una entrada de registro final λ′ que confirma la finalización o el rollback.

- **RFC 3161 (Timestamping):** Cuando esté disponible, las entradas de registro incorporan marcas temporales confiables de Autoridades de Sellado de Tiempo (TSA) externas para establecer irrefutabilidad temporal.

Al restringir toda interacción del usuario a través de esta capa de control mínima y matemáticamente verificable, la infraestructura VIGÍA asegura que las operaciones forenses permanezcan transparentes, repetibles y defendibles en procedimientos legales adversariales.

### 1. Назначение модуля и его место в архитектуре

Модуль `vigia/cli.py` представляет собой основной управляющий уровень командного интерфейса (CLI) цифрокриминалистической среды VIGÍA. Его архитектурное предназначение заключается в функционировании в качестве единственного детерминированного шлюза, посредством которого следователь преобразует структурированные высокоуровневые директивы в однозначные низкоуровневые системные инструкции. Функционируя в пределах фиксированного объёма 5956 байт, данный модуль выступает в роли лексико-синтактико-семантического преобразователя, устраняющего интерпретационную двусмысленность при приёме криминалистических команд. В отличие от универсальных синтаксических анализаторов командной строки, допускающих недетерминированное поведение посредством нечёткого сопоставления или эвристического автодополнения, `vigia/cli.py` сконструирован на основе строгого детерминированного контракта: для любой заданной входной строки и состояния системы модуль порождает в точности одно синтаксическое дерево, один путь исполнения и одну поддающуюся аудиту запись журнала. Указанное свойство является фундаментальным для допустимости цифровых доказательств в соответствии со стандартом *Daubert* и требованиями воспроизводимости, установленными в ISO/IEC 27037:2012.

Архитектурно `vigia/cli.py` занимает Уровень 3 (Представление и Управление) эталонной модели VIGÍA, осуществляя медиацию между следователем-пользователем на Уровне 4 и сервисами криминалистического ядра на Уровне 2. Модуль не осуществляет непосредственного изъятия доказательств, криптографического хеширования или хранения цепочки хранения; вместо этого он оркестрирует вызовы модулей `vigia/acquisition.py`, `vigia/custody.py` и `vigia/orchestrator.py` посредством строго валидированного протокола диспетчеризации команд. Централизуя всю пользовательскую управляющую логику в минимальной поддающейся аудиту поверхности, модуль гарантирует, что каждое взаимодействие с криминалистическим субстратом подвергается синтаксической валидации, верификации привилегий и внесению в журнал, устойчивый к подделке, ещё до начала исполнения.

### 2. Математические основания

Проектирование `vigia/cli.py` базируется на теории формальных языков и детерминированных системах перехода состояний. Определим входной алфавит как множество символов UTF-8 Σ. Тогда множество всех возможных командных строк есть Σ*. Модуль реализует детерминированный лексический анализатор ℒ, отображающий входную строку *c* ∈ Σ* в конечную последовательность лексем τ = (t₁, t₂, …, tₙ) ∈ T*, где T — словарь лексем, определённый грамматикой команд G_vigia. Формально:

ℒ: Σ* → T*

Синтаксический анализатор 𝒫 представляет собой детерминированный автомат с магазинной памятью (или эквивалентный ему восходящий/нисходящий анализатор LL(k)), потребляющий τ и порождающий абстрактное синтаксическое дерево (АСД) *a* ∈ 𝓐, где 𝓐 — множество всех корректно построенных АСД:

𝒫: T* → 𝓐

Семантическая валидация моделируется как предикатная функция 𝒮: 𝓐 → {0, 1}, причём 𝒮(*a*) = 1 тогда и только тогда, когда АСД удовлетворяет всем контекстным ограничениям (корректные идентификаторы доказательств, авторизованные учётные данные пользователя, темпорально согласованные метки времени и совместимые целевые подсистемы). Множество допустимых команд, следовательно:

𝒱 = { *a* ∈ 𝓐 | 𝒮(*a*) = 1 }

Диспетчеризация команд формализуется функцией перехода состояний Δ. Пусть 𝓢 обозначает глобальное пространство состояний системы (включающее переменные среды, открытые дескрипторы доказательств и битовые карты привилегий), а 𝓞 — пространство наблюдаемых выходных данных (коды возврата, потоки stdout/stderr и записи журнала). Тогда:

Δ: 𝒱 × 𝓢 → 𝓢 × 𝓞

Центральный инвариант модуля — детерминизм: для любой допустимой команды *a* ∈ 𝒱 и любого достижимого состояния *s* ∈ 𝓢 переход является синглетоном:

|Δ(*a*, *s*)| = 1

Это означает, что траектория исполнения является функцией, а не отношением, что обеспечивает воспроизводимость.

Журналирование цепочки хранения моделируется инъективной функцией Λ, отображающей каждую криминалистическую операцию в уникальную запись журнала. Пусть 𝓔 — пространство идентификаторов доказательств, 𝓤 — пространство хешей учётных данных пользователя, 𝓣 — пространство доверенных меток времени, а 𝓛 — пространство записей реестра. Тогда:

Λ: 𝓔 × 𝓤 × 𝓣 × 𝒱 → 𝓛

Каждая запись λ ∈ 𝓛 криптографически связывается с соответствующей операцией посредством однонаправленной хеш-функции *H* (типично SHA-256 или SM-3 при соблюдении стандарта GB/T):

λ = *H*(*e* || *u* || *t* || *a* || nonce)

где || обозначает конкатенацию, а nonce ∈ ℕ — монотонно возрастающий порядковый номер, генерируемый модулем `vigia/audit.py` для предотвращения атак повторного воспроизведения.

### 3. Алгоритмическое описание

Операционный алгоритм `vigia/cli.py` проходит восемь строго упорядоченных фаз, каждая из которых в худшем случае демонстрирует линейную или линейно-логарифмическую временну́ю сложность относительно размера входных данных *n* = |*c*|.

**Фаза 1: Лексический анализ.** Лексический анализатор посимвольно сканирует исходную строку *c* с использованием ДКА, имеющего |Σ| переходов. Токенизация выполняется за время O(*n*) и требует O(1) дополнительной памяти (без учёта выходного массива лексем).

**Фаза 2: Синтаксический разбор.** Нисходящий рекурсивный анализатор потребляет τ в соответствии с G_vigia. Грамматика намеренно спроектирована как LL(1), что исключает возвраты и гарантирует время разбора O(*n*). Результатом является АСД *a*, узлы которого представляют команды, аргументы, флаги и целевые подсистемы.

**Фаза 3: Семантическая валидация.** Валидатор осуществляет обход *a* в постфиксном порядке, проверяя: (i) существование всех идентификаторов доказательств *e* ∈ 𝓔 в реестре активных дел, управляемом `vigia/evidence.py`; (ii) наличие у вызывающего пользователя *u* ∈ 𝓤 необходимой битовой карты привилегий *p* для запрошенного класса операций; (iii) выполнение темпорального ограничения *t*<sub>cur</sub> ≥ *t*<sub>last</sub> для журналов цепочки хранения, допускающих только добавление; (iv) готовность целевой подсистемы (изъятие, хранение, оркестрация) к приёму новых команд.

**Фаза 4: Верификация привилегий и целостности.** Перед диспетчеризацией модуль вычисляет криптографическую контрольную сумму АСД, *H*(*a*), и сверяет её с манифестом целостности, поддерживаемым `vigia/hashing.py`. Любое расхождение приводит к аварийному завершению с кодом возврата ε = 255 и инициированию инцидентной записи.

**Фаза 5: Атомарное журналирование (Write-Ahead).** Следуя протоколу WAL, модуль обращается к `vigia/audit.py` для сохранения λ = Λ(*e*, *u*, *t*, *a*) в устойчивое к подделке хранилище до начала исполнения операции. Запись принудительно синхронизируется (fsync) на энергонезависимый носитель, гарантируя, что даже при катастрофическом отказе невозможно уничтожить свидетельство намерения выполнить операцию.

**Фаза 6: Диспетчеризация команд.** Валидированное АСД сериализуется в каноническое межмодульное сообщение *m* ∈ ℳ и передаётся через локальный доменный сокет или in-memory очередь целевой подсистеме. Отображение типа узла АСД на подсистему является инъективным:

dispatch: {acquisition, custody, orchestration, hash_verify} → {`vigia/acquisition.py`, `vigia/custody.py`, `vigia/orchestrator.py`, `vigia/hashing.py`}

**Фаза 7: Исполнение и захват выходных данных.** Целевая подсистема исполняет операцию и возвращает структурированный ответ *r* ∈ 𝓡. CLI захватывает код возврата ε, поток stdout σ и поток stderr δ, инкапсулируя их в наблюдаемый выход *o* ∈ 𝓞.

**Фаза 8: Пост-исполнительная верификация.** Модуль выполняет дельта-проверку между предоперационным состоянием *s* и постоперационным состоянием *s*′, удостоверяясь, что произошли исключительно заявленные побочные эффекты. Формируется финальная запись журнала λ′, подтверждающая завершение или откат.

### 4. Спецификации входных и выходных данных

**Входные данные:**
- **Командный вектор:** argv = [prog, arg₁, arg₂, …, argₘ], где prog ≡ "vigia" и argᵢ ∈ Σ*.
- **Окружение:** Ограниченное отображение переменных среды ℰ ⊂ (String × String), санитизированное модулем `vigia/sandbox.py`.
- **Стандартный ввод:** ℐ, используется исключительно для передаваемых по каналу метаданных доказательств или определений рабочих процессов в формате JSON.
- **Управляющие сигналы:** SIGINT и SIGTERM перехватываются и преобразуются в корректные последовательности завершения с обязательной финализацией журнала.

**Выходные данные:**
- **Код возврата:** ε ∈ {0} ∪ ℰ<sub>err</sub>, где 0 обозначает успех, а ℰ<sub>err</sub> = {1, 2, …, 255} представляет собой биекцию на перечисленные режимы отказа (синтаксическая ошибка, отказ в доступе, тайм-аут подсистемы, нарушение целостности).
- **Стандартный вывод:** σ ∈ Σ*, форматируемый как JSON или как неформатированный текст в соответствии с флагом `--format`.
- **Стандартный вывод ошибок:** δ ∈ Σ*, содержащий структурированные объекты ошибок в стиле RFC 7807.
- **Дополнение журнала:** Атомарные записи в аудиторский реестр VIGÍA через `vigia/audit.py`.

### 5. Гарантии детерминизма

Модуль обеспечивает следующие формальные гарантии детерминизма, каждая из которых необходима для криминалистической воспроизводимости и судебной допустимости:

1. **Функциональный детерминизм:** Для всех достижимых состояний *s* ∈ 𝓢 и всех допустимых входных данных *x* ∈ 𝒱 траектория исполнения Tr(cli, *s*, *x*) является единственной. Формально:
   ∀*s* ∈ 𝓢, ∀*x* ∈ 𝒱: |Tr(cli, *s*, *x*)| = 1

2. **Темпоральная монотонность:** Все метки времени *t*, генерируемые или потребляемые модулем, удовлетворяют *t*<sub>*i*+1</sub> ≥ *t*<sub>*i*</sub>; данное требование обеспечивается монотонными источниками времени (CLOCK_MONOTONIC в POSIX, QueryPerformanceCounter в Windows) и перекрёстно верифицируется по доверенному источнику меток времени, заданному в `vigia/audit.py`.

3. **Неизменяемость журнала:** После фиксации записи λ на Фазе 5 её изменение становится вычислительно неосуществимым без обнаружения благодаря хеш-цепочке λ<sub>*i*</sub> = *H*(λ<sub>*i*−1</sub> || payload<sub>*i*</sub>).

4. **Воспроизводимость по *Daubert*:** Поскольку поведение модуля является чистой функцией от входных данных и состояния, независимые эксперты могут точно реплицировать любую криминалистическую операцию, удовлетворяя критериям *Daubert* (тестируемость, известные частоты ошибок, соответствие общепринятым стандартам).

5. **Изоляция от недетерминированных подсистем:** Уровень CLI не производит выборку из случайных распределений, не зависит от планирования потоков для семантических результатов и не кэширует результаты между вызовами, за исключением случаев явного указания детерминированных ключей кэширования.

### 6. Интеграция со связанными модулями VIGÍA

`vigia/cli.py` функционирует как центральная нервная система платформы, взаимодействуя со следующими базовыми модулями:

- **`vigia/acquisition.py`:** Принимает валидированные команды изъятия для посекторного клонирования, захвата оперативной памяти и перехвата сетевых пакетов. CLI гарантирует, что каждая директива изъятия содержит обязательный идентификатор доказательства и подпись хранителя до момента диспетчеризации.
- **`vigia/custody.py`:** Дополняет записи цепочки хранения для каждого доказательства, затронутого в течение сеанса. CLI генерирует дескрипторы событий хранения, которые данный модуль иммортализирует в своём реестре, допускающем только добавление.
- **`vigia/orchestrator.py`:** Принимает ориентированные ациклические графы (DAG) криминалистических задач, кодированные в виде JSON-схем рабочих процессов. CLI валидирует топологию DAG (отсутствие циклов, наличие терминальных узлов) перед отправкой.
- **`vigia/hashing.py`:** Запрашивает криптографическую верификацию целостности доказательств. CLI прозрачно инжектирует шаги верификации хеша до и после операций, модифицирующих или транспортирующих файлы доказательств.
- **`vigia/audit.py`:** Предоставляет устойчивое к подделке хранилище для всех записей λ. CLI опирается на данный модуль для генерации nonce, аттестации меток времени и запечатывания журналов.
- **`vigia/evidence.py`:** Поддерживает реестр активных контейнеров доказательств. CLI обращается к этому реестру на Фазе 3 семантической валидации для подтверждения существования целевого доказательства и отсутствия конфликтующих блокировок.

### 7. Соответствие стандартам и криминалистическая допустимость

`vigia/cli.py` спроектирован с учётом удовлетворения множества юрисдикционных и технических стандартов:

- **Стандарт *Daubert* (США):** Детерминированное поведение модуля допускает его тестирование, рецензирование и количественную оценку частот ошибок (теоретическая частота ошибок ε → 0 для синтаксически корректных команд при штатном функционировании системы).
- **ISO/IEC 27037:2012:** Модуль обеспечивает повторяемые процедуры изъятия и обращения с доказательствами, гарантируя сохранение целостности цифровых доказательств на этапах от идентификации до сохранения.
- **GB/T 29360-2012 (Китай):** Соответствие национальным стандартам КНР по экспертизе электронных данных достигается посредством детерминированного журналирования операций, криптографической верификации целостности и стандартизированных форматов выходных данных.
- **MLPS 2.0 (Многоуровневая схема защиты):** Верификация привилегий и генерация аудиторского следа модуля соответствуют требованиям Уровня 3 (Контролируемая защита) в части аудита безопасности и операционной подотчётности.
- **RFC 3161 (Штампование времени):** При наличии соответствующей инфраструктуры записи журнала включают доверенные метки времени от внешних Центров Штампования Времени (TSA), устанавливая темпоральную неопровержимость.

Сужая все пользовательские взаимодействия через данный минимальный, математически верифицируемый управляющий уровень, платформа VIGÍA гарантирует, что криминалистические операции остаются прозрачными, воспроизводимыми и обоснованными в состязательном судебном процессе.

### 1. 模块目的与架构定位

`vigia/cli.py` 模块是 VIGÍA 数字取证框架的核心命令行接口（CLI）控制层。其架构职责在于充当唯一确定性的网关，将调查人员输入的结构化高层指令转译为无歧义的低层系统指令。该模块以固定的 5956 字节体积运行，作为词法—句法—语义转换器，在取证命令注入过程中消除一切解释性歧义。与通用 CLI 解析器通过模糊匹配或启发式自动补全容忍非确定性行为不同，`vigia/cli.py` 在严格的确定性契约下构建：对于任意给定的输入字符串与系统状态，该模块仅生成唯一的解析树、唯一的执行路径以及唯一的可审计日志条目。该属性是数字证据在 *Daubert* 标准下获得可采性的根基，亦符合 ISO/IEC 27037:2012 所规定的可重复性要求。

在 VIGÍA 参考模型中，`vigia/cli.py` 位于第 3 层（表示与控制层），在第 4 层的人机交互界面与第 2 层的取证内核服务之间承担中介职能。该模块并不直接执行证据获取、密码学哈希运算或保管链存储，而是通过严格校验的命令分派协议，对 `vigia/acquisition.py`、`vigia/custody.py` 与 `vigia/orchestrator.py` 进行调用编排。通过将全部面向用户的控制逻辑集中于最小化、可审计的表面层，该模块确保所有与取证底座的交互在执行前均经历句法校验、权限核验与抗篡改日志记录。

### 2. 数学基础

`vigia/cli.py` 的设计建立在形式语言理论与确定性状态转移系统之上。设输入字母表为 UTF-8 字符集 Σ，则所有可能的命令字符串集合为 Σ*。该模块实现确定性词法分析器 ℒ，将输入字符串 *c* ∈ Σ* 映射为有限 Token 序列 τ = (t₁, t₂, …, tₙ) ∈ T*，其中 T 为由 VIGÍA 命令文法 G_vigia 定义的词汇表。形式化表达为：

ℒ: Σ* → T*

语法分析器 𝒫 构成一个确定性下推自动机（或等价的 LL(k) 递归下降分析器），其消耗 τ 并生成抽象语法树（AST）*a* ∈ 𝓐，𝓐 为所有合法 AST 的集合：

𝒫: T* → 𝓐

语义校验建模为谓词函数 𝒮: 𝓐 → {0, 1}，当且仅当 AST 满足全部上下文约束（合法证据标识符、已授权用户凭证、时间一致的时间戳、兼容的目标子系统）时，𝒮(*a*) = 1。因此，合法命令集合为：

𝒱 = { *a* ∈ 𝓐 | 𝒮(*a*) = 1 }

命令分派形式化为状态转移函数 Δ。记 𝓢 为全局系统状态空间（涵盖环境变量、已打开的证据句柄与权限位图），𝓞 为可观测输出空间（退出码、标准输出/标准错误流、日志条目），则分派函数为：

Δ: 𝒱 × 𝓢 → 𝓢 × 𝓞

该模块的核心不变量为确定性：对于任意合法命令 *a* ∈ 𝒱 与任意可达状态 *s* ∈ 𝓢，其状态转移均为单例：

|Δ(*a*, *s*)| = 1

这意味着执行轨迹是函数而非关系，从而保证可复现性。

保管链日志建模为单射函数 Λ，将每项取证操作映射至唯一日志条目。记 𝓔 为证据标识符空间，𝓤 为用户凭证哈希空间，𝓣 为可信时间戳空间，𝓛 为账本条目空间，则有：

Λ: 𝓔 × 𝓤 × 𝓣 × 𝒱 → 𝓛

每条目 λ ∈ 𝓛 通过单向哈希函数 *H*（在符合 GB/T 规范时通常采用 SHA-256 或 SM-3）与其操作进行密码学绑定：

λ = *H*(*e* || *u* || *t* || *a* || nonce)

其中 || 表示连接运算，nonce ∈ ℕ 为由 `vigia/audit.py` 生成的单调递增序列号，用于防范重放攻击。

### 3. 算法描述

`vigia/cli.py` 的运行算法按严格顺序历经八个阶段，每阶段相对于输入规模 *n* = |*c*| 的最坏时间复杂度均为线性或线性对数级。

**阶段 1：词法分析。** 词法分析器以 DFA 对原始输入串 *c* 逐字符扫描，状态转移规模为 |Σ|。分词过程时间复杂度为 O(*n*)，辅助空间复杂度为 O(1)（不含输出 Token 数组）。

**阶段 2：句法分析。** 递归下降分析器依照 G_vigia 消耗 τ。该文法刻意设计为 LL(1)，从而消除回溯并保证 O(*n*) 的分析时间。输出 AST *a* 的各节点分别表征命令、参数、标志位及目标子系统。

**阶段 3：语义校验。** 校验器以后序遍历方式处理 *a*，依次核验：(i) 所有证据标识 *e* ∈ 𝓔 均存在于 `vigia/evidence.py` 管理的在案注册表中；(ii) 调用用户 *u* ∈ 𝓤 具备所请求操作类别所需的权限位图 *p*；(iii) 时间约束 *t*<sub>cur</sub> ≥ *t*<sub>last</sub> 对仅追加式保管链日志成立；(iv) 目标子系统（如获取、保管、编排）处于可接收新命令的状态。

**阶段 4：权限与完整性核验。** 在分派前，模块计算 AST 的密码学校验和 *H*(*a*)，并与 `vigia/hashing.py` 维护的完整性清单进行比对。任何偏差均导致执行中止，返回退出码 ε = 255，并触发事件记录。

**阶段 5：原子日志记录（预写式）。** 遵循 WAL 协议，模块调用 `vigia/audit.py` 将 λ = Λ(*e*, *u*, *t*, *a*) 持久化至抗篡改存储，早于操作实际执行。日志通过 fsync 强制同步至非易失介质，确保即便发生灾难性故障，亦无法抹除执行意图的证据。

**阶段 6：命令分派。** 经校验的 AST 被序列化为标准跨模块消息 *m* ∈ ℳ，通过本地域套接字或内存队列传输至目标子系统。AST 节点类型到子系统的映射为单射：

dispatch: {acquisition, custody, orchestration, hash_verify} → {`vigia/acquisition.py`, `vigia/custody.py`, `vigia/orchestrator.py`, `vigia/hashing.py`}

**阶段 7：执行与捕获。** 目标子系统执行操作并返回结构化响应 *r* ∈ 𝓡。CLI 捕获返回码 ε、标准输出流 σ 与标准错误流 δ，并将其封装为可观测输出 *o* ∈ 𝓞。

**阶段 8：执行后校验。** 模块对操作前状态 *s* 与操作后状态 *s*′ 执行增量检查（delta-check），确认仅发生声明的副作用，并输出终态日志条目 λ′ 以确认完成或回滚。

### 4. 输入/输出规范

**输入：**
- **命令向量：** argv = [prog, arg₁, arg₂, …, argₘ]，其中 prog ≡ "vigia"，且 argᵢ ∈ Σ*。
- **环境变量：** 受限环境变量映射 ℰ ⊂ (String × String)，由 `vigia/sandbox.py` 完成净化处理。
- **标准输入：** ℐ，仅用于管道传输的证据元数据或 JSON 工作流定义。
- **控制信号：** SIGINT 与 SIGTERM 被拦截并转换为有序关闭序列，强制完成日志终结。

**输出：**
- **退出码：** ε ∈ {0} ∪ ℰ<sub>err</sub>，其中 0 表示成功，ℰ<sub>err</sub> = {1, 2, …, 255} 与枚举故障模式（句法错误、权限拒绝、子系统超时、完整性失效）构成双射。
- **标准输出：** σ ∈ Σ*，依据 `--format` 标志以 JSON 或纯文本格式输出。
- **标准错误：** δ ∈ Σ*，包含符合 RFC 7807 规范的结构化问题详情对象。
- **日志追加：** 通过 `vigia/audit.py` 向 VIGÍA 审计账本执行原子写操作。

### 5. 确定性保证

该模块提供以下形式化确定性保证，每项均对取证可重复性与司法可采性至关重要：

1. **函数式确定性：** 对于所有可达状态 *s* ∈ 𝓢 与所有合法输入 *x* ∈ 𝒱，执行轨迹 Tr(cli, *s*, *x*) 唯一。形式化表述为：
   ∀*s* ∈ 𝓢, ∀*x* ∈ 𝒱: |Tr(cli, *s*, *x*)| = 1

2. **时间单调性：** 模块生成或消费的全部时间戳 *t* 均满足 *t*<sub>*i*+1</sub> ≥ *t*<sub>*i*</sub>，该约束由单调时钟源（POSIX 下的 CLOCK_MONOTONIC、Windows 下的 QueryPerformanceCounter）强制执行，并与 `vigia/audit.py` 引用的可信时间戳机构进行交叉核验。

3. **日志不可变性：** 日志条目 λ 在阶段 5 提交后，若无检测即行修改在计算上不可行，此性质由哈希链 λ<sub>*i*</sub> = *H*(λ<sub>*i*−1</sub> || payload<sub>*i*</sub>) 保障。

4. **Daubert 框架下的可复现性：** 鉴于模块行为是其输入与状态的纯函数，独立调查人员可精确复现任何取证操作，从而满足 *Daubert* 标准的可检验性、已知错误率与既定标准遵循度等准则。

5. **非确定性子系统隔离：** CLI 层不从随机分布中采样，不依赖线程调度以产生语义结果，也不在调用间缓存结果，除非由确定性缓存键显式指示。

### 6. 与相关 VIGÍA 模块的集成

`vigia/cli.py` 作为框架的中枢神经系统，与以下核心模块交互：

- **`vigia/acquisition.py`：** 接收经校验的获取命令，用于位流镜像、内存捕获及网络数据包拦截。CLI 确保每项获取指令在分派前均包含强制性的证据标识与保管人签名。
- **`vigia/custody.py`：** 为会话期间接触到的每项证据追加保管链记录。CLI 生成保管事件描述符，由该模块在其仅追加账本中永久固化。
- **`vigia/orchestrator.py`：** 接收以 JSON 工作流模式编码的法证任务有向无环图（DAG）。CLI 在提交前验证 DAG 拓扑（无环性、存在终止节点）。
- **`vigia/hashing.py`：** 请求对证据完整性进行密码学校验。CLI 在修改或传输证据文件的操作前后透明注入哈希校验步骤。
- **`vigia/audit.py`：** 为所有日志条目 λ 提供抗篡改存储。CLI 依赖该模块完成 nonce 生成、时间戳认证与日志封存。
- **`vigia/evidence.py`：** 维护活跃证据容器的注册表。CLI 在阶段 3 的语义校验中查询该注册表，以确认目标证据存在且未处于冲突锁定状态。

### 7. 标准合规性与取证可采性

`vigia/cli.py` 的设计旨在同时满足多司法管辖区与技术标准：

- ***Daubert* 标准（美国）：** 模块的确定性行为允许进行测试、同行评审及错误率量化（在正常系统运行下，句法合法命令的理论错误率 ε → 0）。
- **ISO/IEC 27037:2012：** 模块强制执行可重复的证据获取与处理流程，确保数字证据的完整性自识别阶段起直至保全阶段均受到保护。
- **GB/T 29360-2012（中国）：** 通过确定性操作日志记录、密码学完整性校验及标准化输出格式，达到中国电子数据取证检验国家标准要求。
- **MLPS 2.0（网络安全等级保护制度）：** 模块的权限校验与审计追踪生成能力符合第三级（监督保护级）对安全审计与运行问责的要求。
- **RFC 3161（时间戳）：** 在可用条件下，日志条目引入外部可信时间戳机构（TSA）的时间戳，以建立时间上的不可抵赖性。

通过将所有用户交互约束于这一最小化、数学上可验证的控制层，VIGÍA 框架确保取证操作在对抗性法律程序中保持透明、可重复与可辩护。
