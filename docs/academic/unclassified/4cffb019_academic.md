**Fundamentos matemáticos.** La arquitectura teórica del módulo se sustenta en el álgebra relacional, la teoría de grafos y la semántica de punto fijo.

Definí el repositorio de patrones forenses como una estructura relacional S = (T, C, I, R), donde T = {t₁, t₂, ..., tₙ} representa el conjunto finito de tablas (relaciones); C: T → P(A) es una asignación que mapea cada tabla a su conjunto de atributos A; I denota el conjunto de restricciones de integridad, abarcando claves primarias, restricciones de unicidad, restricciones de verificación (*CHECK*) y dependencias de clave foránea; y R representa el conjunto de relaciones de indexación sobre subconjuntos de atributos.

Las restricciones de clave foránea inducen un grafo dirigido de dependencias G = (V, E), donde cada vértice v ∈ V corresponde a una tabla t ∈ T, y cada arista dirigida e = (u, v) ∈ E representa una restricción de clave foránea desde la tabla u que referencia a la tabla v. El módulo impone que G sea un grafo dirigido acíclico (DAG). El algoritmo de creación efectúa un ordenamiento topológico sobre G para producir un orden lineal τ: {1, ..., n} → T tal que, para toda arista (u, v) ∈ E, se cumple τ⁻¹(u) < τ⁻¹(v). Este orden garantiza que las tablas referenciadas sean instanciadas antes que las tablas que las referencian, preservando la integridad referencial en todos los estados intermedios y previniendo la generación de tuplas huérfanas durante la transición de Ω₀ a Ω*.

Denotá con Φ: Σ → Σ la función de transición de estado implementada por el módulo, donde Σ es el conjunto de todos los estados posibles de la base de datos. El módulo garantiza idempotencia: para cualquier estado s ∈ Σ, si s ya satisface el invariante del esquema objetivo (es decir, s ⊨ Ω*), entonces Φ(s) = s. Formalmente, Φ es un operador de proyección que satisface Φ ∘ Φ = Φ. Esta propiedad resulta crítica para la reproducibilidad forense; la ejecución repetida sobre un repositorio existente y no modificado debe reproducir un estado esquemático idéntico sin mutar datos existentes ni metadatos de cadena de custodia.

Para verificar la equivalencia esquemática entre ejecuciones, el módulo computa un hash criptográfico sobre una serialización canónica de S. Sea η: S → {0,1}* una función de codificación canónica que mapea la estructura del esquema a una cadena de bytes normalizada con ordenamiento determinista de claves, espacios en blanco normalizados y *endianness* independiente de la plataforma. El hash del esquema se define como H(S) = SHA-256(η(S)). La igualdad de hashes H(S₁) = H(S₂) implica isomorfismo estructural entre los esquemas S₁ y S₂ con probabilidad abrumadora, acotada inferiormente por la resistencia a colisiones de SHA-256.

**Descripción algorítmica.** El módulo ejecuta el siguiente procedimiento determinista de seis fases.

*Fase 1: Ingesta y validación de configuración.* El módulo ingiere el manifiesto de configuración M (predeterminado: `vigia_schema.toml`), el cual especifica de manera declarativa el esquema objetivo S, el tipo de *backend* de almacenamiento (SQLite, PostgreSQL o basado en sistema de archivos) y anulaciones ambientales opcionales. *Fase 2: Cómputo de hash canónico y adquisición de bloqueo.* El módulo computa H(S) a partir de M. Luego, adquiere un bloqueo consultivo exclusivo sobre la ruta del repositorio objetivo P (mediante bloqueo a nivel de sistema de archivos para *backends* basados en archivos, o bloqueos `LOCK TABLE` / consultivos a nivel de base de datos para PostgreSQL) para prevenir condiciones de carrera durante despliegues concurrentes de CI o inicializaciones paralelas de estaciones de trabajo forenses.

*Fase 3: Reconocimiento de estado.* El módulo consulta el estado existente en P. Si P se halla no inicializado (estado vacío Ω₀), la ejecución avanza a la Fase 4. Si P contiene un esquema existente S', el módulo computa H(S') y lo compara con H(S). Si H(S') = H(S), el módulo realiza una verificación completa de restricciones (Fase 5) y finaliza sin mutación, registrando un evento `IDEMPOTENT_VERIFY`. Si H(S') ≠ H(S), el módulo eleva una excepción `SchemaDriftException` y finaliza con código de salida 2, impidiendo la modificación inadvertida de un repositorio no conforme o potencialmente probatorio.

*Fase 4: Materialización del esquema.* El módulo ordena topológicamente el grafo de dependencias G(S) para producir el orden τ. Para cada tabla t en τ: (a) genera la sentencia de Lenguaje de Definición de Datos (DDL) `CREATE TABLE t(...)`; (b) ejecuta la sentencia atómicamente contra el *backend* de almacenamiento; (c) popula registros centinela obligatorios (por ejemplo, `chain_of_custody_root`, `signature_baseline_epoch`) utilizando marcas temporales deterministas derivadas de la variable de entorno de compilación `SOURCE_DATE_EPOCH`, garantizando salidas idénticas a nivel de bit entre reconstrucciones. Tras la creación de tablas, genera índices, *triggers* y vistas según lo especificado en I.

*Fase 5: Verificación de integridad.* El módulo ejecuta verificaciones de integridad específicas del *backend* (por ejemplo, `PRAGMA integrity_check` para SQLite; inspección de catálogos `pg_constraint` y `pg_index` para PostgreSQL). Verificá que cada clave foránea en E resuelva hacia una clave primaria existente, que no existan dependencias circulares y que todas las restricciones `NOT NULL` y `CHECK` sean satisfacibles por los registros centinela.

*Fase 6: Registro de auditoría y terminación.* El módulo escribe un registro de auditoría JSON estructurado L que contiene `module_hash`: "4cffb019", `execution_timestamp_utc` (ISO-8601), `schema_hash`: H(S), `execution_mode` (`CREATE` o `VERIFY`), `repository_path`: P y `exit_code`: 0. Libera el bloqueo consultivo y finaliza con código 0.

**Математические основания.** Теоретическая архитектура модуля опирается на реляционную алгебру, теорию графов и семантику неподвижной точки.

Судебный репозиторий паттернов определим как реляционную структуру S = (T, C, I, R), где T = {t₁, t₂, ..., tₙ} представляет собой конечное множество таблиц (отношений); C: T → P(A) — отображение каждой таблицы на множество её атрибутов A; I обозначает множество ограничений целостности, включающее первичные ключи, ограничения уникальности, ограничения проверки (CHECK) и зависимости внешних ключей; R представляет собой множество индексных отношений над подмножествами атрибутов.

Ограничения внешних ключей индуцируют направленный граф зависимостей G = (V, E), где каждая вершина v ∈ V соответствует таблице t ∈ T, а каждое направленное ребро e = (u, v) ∈ E представляет ограничение внешнего ключа из таблицы u, ссылающееся на таблицу v. Модуль гарантирует, что G является ациклическим направленным графом (DAG). Алгоритм создания выполняет топологическую сортировку графа G для получения линейного упорядочения τ: {1, ..., n} → T такого, что для любого ребра (u, v) ∈ E выполняется τ⁻¹(u) < τ⁻¹(v). Данное упорядочение гарантирует инстанцирование референцируемых таблиц до таблиц, содержащих ссылки, обеспечивая ссылочную целостность на всех промежуточных этапах и предотвращая появление «сиротских» кортежей в процессе перехода от Ω₀ к Ω*.

Пусть Φ: Σ → Σ обозначает функцию перехода состояний, реализованную модулем, где Σ — множество всех возможных состояний базы данных. Модуль гарантирует идемпотентность: для любого состояния s ∈ Σ, если s уже удовлетворяет инварианту целевой схемы (то есть s ⊨ Ω*), то Φ(s) = s. Формально Φ является оператором проектирования, удовлетворяющим условию Φ ∘ Φ = Φ. Данное свойство критически важно для воспроизводимости судебной экспертизы; повторное выполнение относительно существующего, немодифицированного репозитория должно воспроизводить идентичное состояние схемы без изменения существующих данных или метаданных цепочки сохранности.

Для верификации эквивалентности схем между запусками модуль вычисляет криптографический хэш на основе канонической сериализации структуры S. Пусть η: S → {0,1}* — функция канонического кодирования, отображающая структуру схемы на нормализованную байтовую строку с детерминированным упорядочением ключей, нормализованными пробельными символами и платформонезависимым порядком байтов. Хэш схемы определяется как H(S) = SHA-256(η(S)). Равенство хэшей H(S₁) = H(S₂) влечёт структурный изоморфизм схем S₁ и S₂ с подавляющей вероятностью, ограниченной снизу устойчивостью SHA-256 к коллизиям.

**Алгоритмическое описание.** Модуль выполняет следующую детерминированную шестифазную процедуру.

*Фаза 1: Загрузка и валидация конфигурации.* Модуль загружает манифест конфигурации M (по умолчанию: `vigia_schema.toml`), декларативно специфицирующий целевую схему S, тип хранилища (SQLite, PostgreSQL либо файловая система) и опциональные переопределения среды. Манифест M валидируется по отношению к языку определения схем VIGÍA (VSDL) версии 3.2, что гарантирует корректность всех таблиц, атрибутов и ссылок на ограничения, а также отсутствие неопределённых целей внешних ключей.

*Фаза 2: Вычисление канонического хэша и захват блокировки.* Модуль вычисляет H(S) на основе M. Затем захватывается эксклюзивная консультативная блокировка целевого пути репозитория P (посредством файловой блокировки для файловых хранилищ либо блокировок уровня базы данных `LOCK TABLE` / advisory locks для PostgreSQL) с целью предотвращения состояний гонки при параллельных CI-развёртываниях или одновременной инициализации судебных рабочих станций.

*Фаза 3: Разведка состояния.* Модуль опрашивает существующее состояние по пути P. Если P неинициализирован (пустое состояние Ω₀), выполнение переходит к Фазе 4. Если P содержит существующую схему S', модуль вычисляет H(S') и сравнивает его с H(S). При H(S') = H(S) модуль выполняет полную верификацию ограничений (Фаза 5) и завершается без мутации, регистрируя событие `IDEMPOTENT_VERIFY`. При H(S') ≠ H(S) модуль инициирует исключение `SchemaDriftException` и завершается с кодом возврата 2, предотвращая необдуманную модификацию несоответствующего либо потенциально содержащего доказательства репозитория.

*Фаза 4: Материализация схемы.* Модуль топологически сортирует граф зависимостей G(S) для получения упорядочения τ. Для каждой таблицы t в последовательности τ: (a) генерируется оператор языка описания данных (DDL) `CREATE TABLE t(...)`; (b) оператор атомарно исполняется в хранилище; (c) заполняются обязательные сторожевые записи (например, `chain_of_custody_root`, `signature_baseline_epoch`) с использованием детерминированных временных меток, производных от переменной среды сборки `SOURCE_DATE_EPOCH`, что обеспечивает битово-идентичные результаты при пересборке. После создания таблиц развёртываются индексы, триггеры и представления в соответствии со спецификацией I.

*Фаза 5: Верификация целостности.* Модуль запускает специфичные для хранилища проверки целостности (например, `PRAGMA integrity_check` для SQLite; инспекцию каталогов `pg_constraint` и `pg_index` для PostgreSQL). Верифицируется, что каждый внешний ключ из E разрешается в существующий первичный ключ, что отсутствуют циклические зависимости и что все ограничения `NOT NULL` и `CHECK` совместимы со сторожевыми записями.

*Фаза 6: Протоколирование аудита и завершение.* Модуль формирует структурированный журнал аудита в формате JSON L, содержащий поля `module_hash`: "4cffb019", `execution_timestamp_utc` (ISO-8601), `schema_hash`: H(S), `execution_mode` (`CREATE` или `VERIFY`), `repository_path`: P и `exit_code`: 0. Консультативная блокировка снимается, и процесс завершается с кодом 0.

**Спецификации входных и выходных данных.** Модуль принимает следующие входные аргументы: `--repository-path <PATH>` — опциональный путь в файловой системе либо URI подключения к базе данных, по умолчанию принимающий значение переменной среды `VIGIA_REPO_PATH` либо `/var/lib/vigia/patterns/`; `--schema-manifest <FILE>` — опциональный путь к манифесту VSDL, по умолчанию `vigia_schema.toml`; а также `--force-create` — опциональный булев флаг (по умолчанию ложь), который в непроизводственных средах разрешает перезапись схемы при выявлении дрейфа после создания резервной копии. В производственных судебных сборках данный флаг политически отключён с целью предотвращения загрязнения доказательств.

Выходные данные включают: (1) полностью инстанцированную реляционную схему S по пути P; (2) структурированный JSON-журнал аудита L, записываемый в `VIGIA_LOG_DIR/4cffb019_<timestamp>.json`; (3) коды возврата процесса: 0 (успех либо подтверждённая идемпотентность), 1 (ошибка конфигурации или валидации манифеста), 2 (выявлен дрейф схемы), 3 (сбой ввода-вывода либо захвата блокировки).

**Детерминированные гарантии и судебная строгость.** Модуль обеспечивает следующие детерминированные гарантии. *Детерминизм перехода состояний:* для заданного манифеста M и версии программного обеспечения V функция Φ(M, V, Ω₀) всегда порождает идентичное целевое состояние схемы Ω* независимо от архитектуры хоста или системного времени при условии фиксации переменной среды сборки `SOURCE_DATE_EPOCH`. *Идемпотентная повторная входимость:* ∀s ∈ Σ, если s = Ω*, то Φ(s) = s; повторное исполнение не влечёт мутации данных. *Битово-идентичное хэширование схемы:* H(S) воспроизводится на различных платформах благодаря нормализации порядка байтов, упорядочения полей и кодировки символов функцией η(S). *Сохранение цепочки хранения:* сторожевые таблицы метаданных фиксируют происхождение создания схемы без внедрения недетерминированных системных временных меток в саму схему.

Указанные гарантии удовлетворяют стандарту **Daubert** допустимости научных доказательств, поскольку обеспечивают фальсифицируемость метода, известную норму ошибки (фактически нулевую при контролируемых входных данных), подверженность рецензированию и поддержку документированными стандартными операционными процедурами. Соответствие стандарту **GB/T 29360-2012** (Судебная инспекция электронных данных) достигается за счёт структурированного обеспечения целостности, прослеживаемых журналов инициализации и невозможности отказа от версионирования схемы. Кроме того, модуль поддерживает базовые требования **MLPS 2.0** (*Multi-Level Protection Scheme 2.0*), устанавливая фундаментальную схему управления доступом, аудита и классификации паттернов, лежащую в основе высокоуровневых механизмов безопасности.

**Интеграция с родственными модулями VIGÍA.** Модуль ИРСП является строгим предварительным условием для ряда нисходящих подсистем. **Подсистема сигнатурного сопоставления VIGÍA (модуль 8a2f11c3)** потребляет таблицы `signature_patterns` и `bytecode_rules`, инстанцированные настоящим модулем, для загрузки сигнатур, совместимых с YARA, и пользовательских судебных сигнатур. **Уровень загрузки доказательств VIGÍA (модуль 9e4d55a1)** нуждается в таблицах `evidence_objects`, `file_artifacts` и `hash_registry` для персистентности загружаемых цифровых носителей; ссылочная целостность, обеспечиваемая здесь, гарантирует отсутствие нарушений ограничений внешних ключей при массовых транзакциях загрузки. **Регистратор цепочки сохранности VIGÍA (модуль 1b7c88f2)** опирается на сторожевые таблицы `custody_events` и `custody_roots`, инициализированные на Фазе 4, для формирования устойчивых к фальсификации аудиторских следов. **Коррелятор аномалий VIGÍA (модуль 3f9a22e7)** выполняет сложные операции JOIN между таблицами паттернов; топологический порядок таблиц и составные индексные структуры, создаваемые настоящим модулем, оптимизируют планирование запросов для межартефактной корреляции. Наконец, **Компрессор аудита VIGÍA (модуль 7d1e44b0)** архивирует периодические моментальные снимки состояния схемы, используя канонический хэш H(S) в качестве контрольной суммы манифеста для сжатых пакетов репозитория.

Благодаря строгой математической формализации изоморфизма схем, идемпотентному выполнению с семантикой неподвижной точки и обеспечению ссылочной целостности посредством топологической сортировки графов, модуль гарантирует, что каждая аналитическая среда стартует из идентичной, судебно защищённой базовой линии. ## 中文

**模块标识与目的。** VIGÍA模块4cffb019，正式命名为取证模式库初始化模块（Forensic Pattern Repository Initializer, FPRI），是VIGÍA综合数字取证平台中持久化基板实例化的基础例程。其核心功能在于从零状态或未初始化的持久化层中，实例化生成面向特征签名的工件识别所需的完整结构化模式。该模块在连续集成（CI）流水线及系统初始部署阶段执行，确保每一分析实例均在同一取证可信的数据库基线上运行。通过在任意工件摄取或模式匹配操作开始前强制实施参照完整性，本模块保证下游子系统——包括VIGÍA签名匹配引擎、证据摄取层及异常关联器——所面对的均为逻辑一致且严格确定的模式拓扑结构。

FPRI模块在形式上表现为一个确定性状态转移函数，通过严格排序的数据定义操作序列，将空数据库状态Ω₀转换为目标模式状态Ω*。模块提供一个可选的运行时参数`--repository-path`，允许操作者指定非默认存储路径，从而适配分布式存储拓扑、容器化临时环境与隔离测试平台，且不破坏生成模式的规范结构。

**数学基础。** 本模块的理论架构建立在关系代数、图论与不动点语义之上。

将取证模式库定义为关系结构S = (T, C, I, R)，其中T = {t₁, t₂, ..., tₙ}为有限表（关系）集合；C: T → P(A)为每张表至其属性集A的映射；I为完整性约束集合，包括主键、唯一性约束、检查约束（CHECK）及外键依赖；R为属性子集上的索引关系集合。

外键约束导出一个有向依赖图G = (V, E)，其中每个顶点v ∈ V对应一张表t ∈ T，每条有向边e = (u, v) ∈ E表示从表u指向表v的外键约束。模块强制要求G为有向无环图（DAG）。创建算法对G执行拓扑排序，得到线性序τ: {1, ..., n} → T，使得对任意边(u, v) ∈ E，均有τ⁻¹(u) < τ⁻¹(v)。该排序保证被引用表先于引用表实例化，在所有中间状态维持参照完整性，防止从Ω₀向Ω*过渡期间产生孤儿元组，并确保事务的原子性与一致性。

记Φ: Σ → Σ为模块实现的状态转移函数，其中Σ为数据库所有可能状态的集合。模块保证幂等性：对任意状态s ∈ Σ，若s已满足目标模式不变式（即s ⊨ Ω*），则Φ(s) = s。形式上，Φ为满足Φ ∘ Φ = Φ的投影算子。该属性对取证可复现性至关重要；对现有未修改库重复执行必须复现同一模式状态，且不得改变现有数据或监管链元数据。

为验证跨执行的模式等价性，模块基于模式的规范序列化计算密码学哈希。设η: S → {0,1}*为规范编码函数，将模式结构映射为具有确定性键序、规范化空白及平台无关字节序的归一化字节串。模式哈希定义为H(S) = SHA-256(η(S))。哈希相等H(S₁) = H(S₂)以压倒性概率蕴含模式S₁与S₂之间的结构同构，其下界由SHA-256的抗碰撞性保证。

**算法描述。** 模块执行如下确定性六阶段过程。

*阶段1：配置摄取与校验。* 模块摄取配置清单M（默认：`vigia_schema.toml`），该清单以声明式方式指定目标模式S、存储后端类型（SQLite、PostgreSQL或基于文件系统）及可选环境覆盖。模块依据VIGÍA模式定义语言（VSDL）3.2版对M进行校验，确保所有表、属性及约束引用格式正确，且不存在未定义的外键目标。

*阶段2：规范哈希计算与锁获取。* 模块由M计算H(S)。随后对目标库路径P获取独占咨询锁（文件后端采用文件锁，PostgreSQL采用数据库级`LOCK TABLE`或咨询锁），以防止并发CI部署或并行取证工作站初始化时出现竞态条件。

*阶段3：状态侦察。* 模块查询P处的现有状态。若P未初始化（空状态Ω₀），则进入阶段4。若P包含现有模式S'，模块计算H(S')并与H(S)比较。若H(S') = H(S)，模块执行完整约束校验（阶段5）后无变更退出，并记录`IDEMPOTENT_VERIFY`事件。若H(S') ≠ H(S)，模块抛出`SchemaDriftException`并以退出码2终止，防止对不合规或可能存证之库的无意修改。

*阶段4：模式物化。* 模块对依赖图G(S)进行拓扑排序得到序τ。对τ中的每张表t：（a）生成数据定义语言（DDL）语句`CREATE TABLE t(...)`；（b）对存储后端原子执行该语句；（c）使用构建环境变量`SOURCE_DATE_EPOCH`衍生的确定性时间戳填充强制哨兵记录（如`chain_of_custody_root`、`signature_baseline_epoch`），确保重建时输出逐位相同。建表后，按I中的规范创建索引、触发器及视图。此阶段严格遵循事务边界，单点失败触发整体回滚，确保Ω₀至Ω*的状态转换满足原子性要求。

*阶段5：完整性校验。* 模块执行后端专属完整性检查（例如SQLite执行`PRAGMA integrity_check`；PostgreSQL检查`pg_constraint`与`pg_index`系统目录）。校验每条外键边E均解析至已存在的主键，确认无环依赖，并验证所有`NOT NULL`与`CHECK`约束均可被哨兵记录满足。

*阶段6：审计日志与终止。* 模块写入结构化JSON审计日志L，包含字段`module_hash`: "4cffb019"、`execution_timestamp_utc`（ISO-8601）、`schema_hash`: H(S)、`execution_mode`（`CREATE`或`VERIFY`）、`repository_path`: P及`exit_code`: 0。释放咨询锁后以退出码0结束。
